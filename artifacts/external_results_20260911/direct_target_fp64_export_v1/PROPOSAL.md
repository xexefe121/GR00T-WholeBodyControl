Use the identical source checkpoint `9ceef5099ebd154e08a1c2c3784c4e06021d464e607474548763665b24f8f9e7` and normalization. Promote each stored float32 weight, bias, mean and standard deviation exactly to float64. Keep the public 1000-feature input float32, cast it to float64 before normalization, and run all normalization, linear layers and ELU calculations in float64. Cast only the final normalized target to float32. The native reconstruction remains `default_f64 + span_f32.astype(float64) * head_f32.astype(float64)`, with the unchanged final native bounds.

This is explicitly new numerical execution semantics for the same mathematical model. It is not a byte-identical export of the original float32 computation. Do not relax the original tolerance or imply that successful numerical validation establishes connected stability.

ONNX's installed Elu schema allows double, but ORT 1.23.2 CPU registers its Elu kernel only for float. The [official kernel table](https://github.com/microsoft/onnxruntime/blob/v1.23.2/docs/OperatorKernels.md) and [registration source](https://github.com/microsoft/onnxruntime/blob/v1.23.2/onnxruntime/core/providers/cpu/activation/activations.cc) are preserved under `support/`. Use native double ELU for the Torch CPU/GPU reference, and the mathematically equivalent ONNX double expression `Where(x>0,x,Exp(Min(x,0))-1)`. The `Min` bounds the unused positive exponent and avoids spurious overflow. Different exp/ELU implementations can still round differently; the complete unchanged numerical gate decides acceptance.
